# ReID 合并与人脸证据安全修复 · 2026-09-05

这是后续用户批准的代码修复记录，不改变此前部署记录，也不声称本轮已经发布至 5090。
沿用 FastAPI 的 service / schema / model / db 边界；Fable5 只读取相关源码做第二意见，不接触图片、数据库或凭据。

## 修复范围

1. `collapse_occurrences` 要求身份校验时，缺向量、无效向量或无法比较维度均不退回时间合并。未知摄像头独立。
   非单位有效向量先归一化，完整连锁约束保留。仅显式非正身份阈值保留已知摄像头的旧时间模式。
2. 严格人脸提取区分检测为空、多脸弃权、头部关联失败、坐标无效、原图不存在/不可读、临时写入与推理故障。
   带原帧坐标的数据仍只使用原始人体矩形，不回退到可能含旁人的展示裁剪；没有坐标的旧上传图仍严格检测。
3. 人脸负缓存新增原因和输入指纹，默认 300 秒过期。没有原因的旧负缓存以及暂时故障重试；有效旧正缓存继续复用。
   时间戳使用 UTC，SQLite offset-less 缓存时间也按 UTC 解读，不混用本地视频采集时间。
4. 模型名称与预处理倍率分开；只规范化旧的已知放大后缀，不同模型/不同维度不比较。
5. 查询侧锚点保护不变；候选代表帧无可用脸时，在已通过身份合并的同摄像头、时间窗内最多补查 2 帧。
   借用候选脸的身份标记为未验证，即使余弦高或低，也不能触发硬救回/硬排除。已有可用代表帧不被覆盖。
6. 两个检索响应分别增加 `face_coverage`，展示尝试次数、比较次数、可靠/软证据与弃权原因。
   所有计数均为最终筛选前口径；内部组成员 ID 不序列化到响应。

无查询脸时跳过百名候选、借脸正负结果不能硬判、页面迟到响应与未知字段。没有使用真实人员图片。

## 尚需现场验证

Fable5 本轮复审未发现 P1 阻断项，指出的两项可触发 P2 已进一步处理：
搜索与 links 并发首次提取时，缓存使用 SQLite/PostgreSQL 原子 upsert，避免同主键插入冲突丢掉整批缓存；
OpenCV/可选依赖加载异常统一进入可重试弃权，避免原帧读取或裁剪异常中断检索。
另将候选数据库记录缺失独立命名为 `candidate_row_missing`，不与原图文件缺失混用。

保留的兼容边界：没有输入指纹的旧有效正缓存仍按当前提取配置签名复用；若旧媒体曾被原地覆写，不能据此
证明旧正向量依旧对应当前文件，须在确认需要时单独失效这些记录。当前系统按 crop ID 使用不可变媒体。
缓存提交沿用既有请求 Session 边界，未来不要在脸比较前暂存无关未提交业务写入；本轮未扩展为独立事务框架。
SQLite 原子冲突路径和迁移使用隔离数据库回归；PostgreSQL 语句分支尚需对应数据库的集成验收。
本地缺少 mypy、black、pytest-cov，不把 Ruff/pytest 通过等同于严格类型检查或覆盖率统计通过。

先前在 5090 原地复核的 5 张问题查询，原帧/坐标/指纹正常，严格检测提取阶段均没有可用候选。
修复能解释并安全处理这一情况，但不能保证历史背影、低清或遮挡图片会凭空得到可靠人脸。
逐图真实视觉原因尚未确认；尚无独立人工真值集，不能报告准确率提升百分比。
待发布后小批重放问题查询，再以不同人员/不同时段独立划分调参与验收样本，检查误报、漏报和硬过滤误杀。
